여로담 모바일 사용자 경험 분석 리포트

작성일: 2026-09-13 · 대상: 개발 사이트 · 기준 화면: 390 × 844 CSS px

마감 시점 갱신: 보고서 작성 중 별도 작업에서 30bce9c 커밋이 반영됐다. U03·U15·U17은 코드 수정 반영, U08은 CTA 부분 수정을 확인했다. U03은 수정된 실제 함수로 재검사해 현재 핀 1개 → 표 1행을 확인했다. 아래 관찰·스크린샷은 발견 당시 기록을 보존하며, 이 네 항목의 현재 상태는 5절의 갱신표를 우선한다. 수정 후 전체 브라우저 흐름과 프로덕션 배포는 이번 리포트에서 확인하지 않았다.

1. 핵심 판단

여로담은 장소 검색, 다일차 일정, 자료, 공동편집, 공유, 택시 카드까지 갖추고 있다. 지금 모바일에서 가장 필요한 것은 기능을 더 찾게 만드는 것보다, 이미 담은 장소와 만든 일정을 쉽게 읽고 믿을 수 있게 만드는 일이다.

실제 로그인된 여행에서 가장 큰 불편은 다음 다섯 가지였다.

  1. 장소 이름을 알아보기 어렵다. 펼친 목록에서도 ‘육…’, ‘어…’, ‘만천리…’처럼 줄어든다. 번호·작성자·깃발·잠금·택시·삭제가 이름과 같은 줄의 폭을 나눠 쓴다.
  2. ‘동선으로 보기’가 시간표보다 설정부터 보여준다. 이동 중 다음 장소를 확인하려는 사용자가 출발 시각과 최적화 옵션을 다시 마주한다. 읽기 좋은 표는 별도 메뉴 안에 있다.
  3. 여행의 개수와 동선 수치가 화면마다 달라 보인다. 여행 선택 목록의 핀은 20개, 표의 전체 장소는 26곳이다. 같은 동선 화면에는 17.2km·42분, 20.3km·64분, 17.8km·28분이 함께 등장한다.
  4. 모바일의 제한된 세로 공간을 고정 UI가 많이 사용한다. 반보기에서는 검색 결과 한 곳 정도를 볼 수 있지만, 기존 동선이 있는 일정 목록은 이름·탭·요약·도구·고정 CTA 때문에 목록을 읽기 전에 패널을 펼쳐야 한다.
  5. 현재 상태를 설명하는 정보가 부족하다. 저장 완료 여부, 기존 동선과 변경 예정 결과의 차이, 아직 시간표에 들어가지 않은 장소, 공개 공유와 협업 초대의 관계를 사용자가 추측해야 한다.

우선순위는 일정 데이터 일관성 → 장소명과 시간표 가독성 → 저장·공유 상태 설명 → 여행 중 실행 기능 순서가 적절하다. 대규모 색상·브랜드 변경이나 기능 전면 재개발부터 시작할 필요는 없다.

2. 조사 방법과 해석 범위

검토 환경

  • 사용자가 로그인해 둔 기존 Chrome 창을 사용했다. 계정 화면에서 시험용 계정 user1@mail.com을 확인했다. 다른 계정으로 전환하지 않았다.
  • 시작 여행은 ‘춘천여행가자 우리’, 5일 구성, 최초 확인 일차는 3일차·핀 7개였다. 협업자가 추가한 핀과 기존 생성 동선, 여행 자료 10개가 있었다.
  • 시작 때 개발자 도구 높이가 818로 표시되어 844로 다시 맞췄다. 주요 검토는 390 × 844에서 진행했다.
  • Chrome 반응형 화면 검토이며 실제 iPhone 14 Safari 검증은 아니다. iOS 키보드, 손가락 드래그, 뒤로가기 제스처, VoiceOver, 실제 이동 중 GPS·통신 품질·배터리 사용량은 측정하지 않았다.
  • Windows 접근성 트리로 버튼·문구·위치를 확인하고 UI를 조작했다. 화면 증거는 해당 Chrome 창의 모바일 영역을 캡처했다. 접근성 API 호출 성공을 실제 손가락 터치 성공과 동일하게 해석하지 않았다.
  • 캡처는 OS 배율이 포함되어 주로 488 × 1055 이미지로 저장되었다. 이것은 CSS 뷰포트 390 × 844의 확대 캡처다. 이미지 픽셀을 그대로 CSS 버튼 크기로 계산하지 않았다.
  • 최초 소스 대조 기준 HEAD는 9351ac6, 마감 시점 HEAD는 30bce9c다. 시작부터 tripActivity.ts, 여러 로케일, KoreaInfoPage.tsx 등에 사용자 미커밋 변경이 있었고, 검토 도중 별도 작업으로 커밋 상태가 바뀌었다. 이 검토에서는 그 변경을 수정·되돌리지 않았다. 개발 사이트 결과를 Netlify 배포 상태와 동일시하지 않았다.

근거 수준

  • 화면 확인: 이번 세션에서 직접 표시와 동작을 확인했다.
  • 코드 확인: 현재 소스에서 관련 동작을 확인했다. 실기기 결과까지 보장하지 않는다.

  • 추가 검증: 재현 조건이나 원인이 확정되지 않은 사항이다.

6. P1 상세 분석

U01. 이름이 핵심인 목록에서 이름에 가장 적은 폭이 남는다

재현: 3일차·핀 7개 → 목록으로 보기 → 패널 전체보기. 협업자가 넣은 음식점 카드를 확인한다.

관찰: 카테고리 제목이 왼쪽 열을 차지하고, 오른쪽 카드에는 순번·작성자·깃발·이름·잠금·택시·삭제가 함께 놓인다. 육대장 후평점은 ‘육…’, 어라운드키친은 ‘어…’처럼 보인다. 접근성 트리의 해당 이름 버튼 폭은 약 53 이미지 px, 화면 배율을 고려하면 약 42 CSS px 수준이었다. 짧은 이름조차 구분하기 어렵다.

원인: 이전 ‘무조건 4글자로 자르기’는 제거되어 있지만 남은 폭 자체가 좁다. PinupBar.tsx는 작성자·깃발·잠금을 각각 렌더링하고, 모바일 CSS는 이름이 더 좁아지는 것을 피하려고 보조 버튼을 36px로 절충한 상태다. 작은 아이콘 문제와 이름 문제를 한 줄 안에서 함께 해결하려고 해서 서로 악화시킨다.

개선: 이름을 2줄까지 사용하고, 카드 첫 줄은 순번·이름·더보기 중심으로 재구성한다. 작성자는 작은 보조 줄로 옮긴다. 필수 여부는 깃발과 잠금 중 하나의 읽기 쉬운 표시로 통합하고, 삭제·택시는 상세/더보기 또는 명확한 별도 동작 줄로 배치한다. 카테고리는 행 옆 고정 열보다 그룹 제목이나 작은 배지가 적합하다.

완료 기준: 390px, 협업자·필수 방문·긴 이름이 동시에 있는 데이터에서 세 장소를 상세창 없이 구분할 수 있어야 한다. 이름을 넓히기 위해 조작 영역을 다시 축소해서는 안 된다.

증거: 펼친 목록 · 관련 컴포넌트 · 모바일 CSS

U02. 목록을 보려면 먼저 패널을 확장해야 한다

관찰: 기존 동선이 있는 반보기 상태에서는 여행명, 3탭, ‘오늘 동선’ 카드, 도구 줄, 고정 CTA가 목록 높이를 소비한다. 첫 장소는 일부만 노출되며 전체 이름을 읽기 어렵다. 전체보기에서도 도구 버튼만 있는 줄 위아래에 여백이 크다.

검색 결과 높이가 0이던 이전 문제와 동일한 버그로 단정하지 않는다. 이번 검색은 반보기에서도 첫 결과가 보였다. 고정 UI에 배정된 높이와 실제 목록의 정보량이 문제다.

개선: 목록 진입은 데이터가 있을 때 전체보기 또는 더 높은 중간 높이를 사용한다. ‘오늘 동선’ 요약과 하단 ‘동선 만들기’ 중 현재 상태에 맞는 주 행동 하나를 둔다. 도구 아이콘은 제목 줄로 합친다. 화면을 내리는 동작은 ‘지도 크게 보기’로 명확히 제공한다.

완료 기준: 기존 동선·협업 핀 7개 조건에서 첫 진입 시 최소 2곳의 전체 식별 정보가 보이고 마지막 장소까지 스크롤할 수 있어야 한다. 키보드가 열렸을 때 별도로 확인한다.

증거: 반보기 접근성 위치 기록 · 전체보기 · 반보기 검색 비교

U03. 표의 장소 개수가 현재 핀보다 많아진다

관찰: 여행 목록의 현재 여행은 핀 20개이고, 일차별 핀 수도 2+10+7+1+0=20개다. 반면 표는 전체 26곳으로 표시한다. 단순 표시 숫자만 고치기 전에 데이터 기준부터 확인해야 한다.

코드 확인: itineraryTable.ts의 rowsForDay()는 이전 동선을 순회하면서 현재 핀에서 찾지 못한 장소도 pinById.get(stop.id) ?? stop으로 되살려 표에 넣는다. 현재 핀과 이전 동선이 달라졌을 때, 표에만 과거 장소가 남을 수 있다.

독립 재현: 현재 핀은 A 한 곳, 과거 동선은 A와 B 두 곳인 입력을 만들고 현재 TypeScript 소스를 변환해 실제 함수를 실행했다. countPinsByDay()는 1, buildItineraryTableRows()는 A·B 두 행을 반환했다. 번역·지역명 포맷 함수만 대체했으며 사용자 계정 데이터에는 쓰지 않았다. 이 재현은 결함 경로를 확인한 것이며 현재 여행에서 차이 난 6곳 각각의 편집 이력까지 추적한 것은 아니다.

영향: 제외한 장소를 사용자가 표에서 다시 방문 대상으로 오해할 수 있다. 표 공유에도 같은 데이터가 쓰이면 동행자에게 다른 일정이 전달될 수 있다. 실제 공개 전송은 하지 않았다.

개선: ‘현재 일정’ 표는 현재 핀을 기준으로 만들고, 이전 동선은 남아 있는 핀의 순서/시각 보조 데이터로만 사용한다. 핀 변경 후 시간표가 오래되면 ‘장소가 변경되어 동선 업데이트가 필요합니다’를 표시한다. 이전 버전 조회가 필요하다면 별도 버전 화면으로 제공한다.

완료 기준: 핀 삭제·추가·다른 날 이동·협업 반영 뒤 목록, 일차 수, 표 행 수가 같은 정의를 사용한다. A만 남긴 입력에 B가 현재 표에 나오지 않아야 한다. 공유 표도 같은 검증을 통과해야 한다.

증거: 전체 표 · 일차별 핀 수 · 여행 목록 수치 기록 · 재현 결과 · 표 생성 코드

U04. 같은 동선 화면의 세 수치를 어떻게 읽어야 하는지 설명이 부족하다

관찰: 상단은 17.2km·42m, 비교 경로는 20.3km·64분, 하단 예상은 17.8km·이동 28분·체류 210분·14:52 끝으로 표시된다. ‘무료도로’가 선택되어 있지만 보이는 비교 행은 최단거리·최소시간이다.

각 수치는 저장된 동선, 외부 비교 경로, 현재 옵션으로 계산한 미리보기처럼 서로 다른 의미일 수 있다. 숫자가 다르다는 사실만으로 어느 계산이 틀렸다고 판정하지 않는다. 기준·시점·포함 장소·이동수단이 구별되지 않는 것은 화면에서 확인된 문제다.

PlannerPage.tsx 상단은 generatedRoute, RouteOptionsPanel.tsx 하단은 generateRoute(pinned, options)의 preview를 사용한다. 비교 결과도 별도 상태다.

개선: 기본 화면은 ‘현재 저장된 일정’을 보여준다. 설정을 바꾸면 ‘변경 미리보기’를 명시하고 기존과 변경 후를 비교한다. 직선 기반 추정/도로 조회 여부, 포함 장소 수, 계산 시점을 제공한다. 선택한 비교 경로가 아직 없으면 그 상태도 표시한다.

완료 기준: ‘왜 42분과 28분이 다른가’를 도움말 없이 알 수 있고, 적용 전후 어떤 값이 저장되는지 설명할 수 있어야 한다. 로딩·실패·추정 폴백에서도 출처가 유지되어야 한다.

증거: 동선 전체보기 · 옵션 계산 코드 · 상단 표시 코드

U05. 결과를 보려는 행동이 편집 양식으로 연결된다

관찰: ‘동선으로 보기’를 선택하면 출발 시각·출발지·이동수단·최적화·‘동선 다시 만들기’가 먼저 나온다. 기존 동선이 있어도 장소별 시간표는 첫 화면에 없다. 시간표를 찾으려면 메뉴 → 표로보기를 알아야 한다.

개선: 세 탭을 사용자의 목적에 맞게 ‘장소 찾기 / 담은 장소 / 일정’으로 정리하는 안을 권한다. ‘일정’의 기본은 시간표·다음 장소·길찾기다. 기존 옵션 패널은 ‘일정 수정’으로 연결한다. 이미 만든 일정에는 ‘동선 만들기’와 ‘다시 짜기’를 중복 노출하지 않는다.

완료 기준: 재방문 사용자가 일정 탭 한 번으로 다음 방문 장소와 시간을 확인한다. 설정 변경은 명시적 편집 동작으로 시작하고, 취소하면 기존 결과로 돌아온다.

증거: 반보기 동선 · 실제로 읽기 좋은 3일차 표

U06. 자동저장이 모바일에서 확신을 주지 못한다

관찰: 점검한 모바일 상단·하단·계정 화면에서 저장 중/저장 완료/연결 끊김의 상시 상태를 찾지 못했다. 협업자 아바타가 있어도 내 변경이 동기화됐는지는 별개의 문제다.

코드 확인: saveStatus는 존재하고 PlannerAppBar에 전달되지만 해당 바는 데스크톱용이다. 모바일 상단에는 같은 상태 표시가 없다. 자동저장 효과는 700ms 디바운스로 실행된다. 이번에 통신을 끊거나 저장 실패를 유도하지 않았으므로 데이터 유실이 발생했다고 주장하지 않는다.

개선: 여행명 옆에 ‘저장됨’, ‘저장 중’, ‘기기에 저장·연결 대기’, ‘저장 실패·다시 시도’를 구분해 제공한다. 상태를 눌렀을 때 마지막 동기화 시점과 재시도 동작을 볼 수 있게 한다. 로컬 저장과 클라우드 저장을 같은 완료 메시지로 처리하지 않는다.

완료 기준: 정상 저장·느린 응답·실패·오프라인·복구에서 사용자가 현재 보존 상태를 알 수 있다. 페이지를 나갔다 돌아와도 마지막 여행 복원 결과가 설명되어야 한다.

증거: 모바일 상단 · 데스크톱 저장 표시 · 자동저장 로직

7. 반복 사용에서 불편한 부분

U07. 목록의 순서가 방문 순서처럼 보이지만 카테고리로 묶여 있다

전체보기에서 음식점 번호 2·3·4가 먼저, 마트 번호 1이 뒤에 나온다. 분류용 목록으로는 타당하지만 ‘목록으로 보기’라는 이름만으로는 방문 순서와 차이를 알기 어렵다. 기본을 방문 순서로 하고 ‘종류별 모아보기’를 선택 옵션으로 제공한다. 번호 드래그와 카테고리 이동도 목적을 구분한다. 완료 기준: 목록 상단에서 어떤 정렬을 보는지 명확하며, 그룹 표시를 바꾸는 일이 실제 방문 순서 변경으로 오인되지 않는다. 증거

U08. 주요 CTA와 세부 정보에 언어·내부 표현이 남아 있다

목록의 Set up route · 동선 만들기 →, 동선 헤더의 42m, 장소 요약의 Places API (New) 데이터, 여행 가이드의 transport, food, other가 확인됐다. 기존 번역 정리 뒤에도 남은 경로다. PinupBar.tsx CTA와 PlaceDetailTabPanels.tsx API 안내는 하드코딩도 확인했다.

선택 언어의 행동 문구와 단위를 사용하고, 데이터 출처는 사용자가 이해하는 서비스명과 필요한 출처 표기를 유지한다. API 버전은 진단 정보로 분리한다. 태그는 ‘교통’, ‘맛집’처럼 의미를 번역하고 분류가 맞는지도 검수한다. 완료 기준: 한국어·영어·일본어에서 핵심 흐름을 열어 번역 누락과 불필요한 혼합 문구가 없다. 이번에 9개 언어 전체를 실행 확인하지는 않았다. 장소 요약 · 가이드

U09. 버튼 확대를 일부 화면에만 적용해 조작성 편차가 크다

패널 핸들과 하단 내비게이션은 개선됐다. 반면 핀의 삭제·택시·필수 버튼은 CSS 36px, 자료의 보조 아이콘과 세부 필터, 장소 상세의 닫기·복사 등은 여전히 작다. 작고 인접한 동작, 특히 삭제와 조회가 붙어 있는 곳부터 개선한다. 카드 이름 영역을 줄이면서 버튼만 확대하면 U01이 악화되므로 행 구조를 함께 바꿔야 한다.

본 리포트의 주요 터치 영역 44~48 CSS px 목표는 제품 사용성 권고다. WCAG 2.2 AA의 2.5.8은 원칙적으로 24×24 CSS px와 간격 등 예외를 다루므로, 44px 미만이라는 이유만으로 위반 판정하지 않는다. 실제 클릭 영역·간격·가상 요소 확장을 함께 검사해야 한다. W3C 기준 설명

U10. 표는 읽기 좋아졌지만 상태 의미를 더 설명해야 한다

3일차 표에서 일부 행은 빨간색이고, 숙소는 11:48, 13:12처럼 단독 시각, 한 장소는 —로 표시된다. 코드상 빨강은 필수 방문, 단독 시각은 도착·출발이 같을 때, 대시는 시각이 없는 경우에 생길 수 있다. 사용자에게는 빨강이 오류·휴무, 대시가 실패처럼 보일 수 있다.

‘필수’ 배지, ‘체류 미설정’, ‘동선 미반영’ 등 실제 데이터 상태에 맞는 설명을 제공한다. 단순히 모든 대시를 같은 문구로 바꾸지 않는다. 숙소는 체크인/숙소 복귀 등 의도가 있으면 따로 표현한다. 완료 기준: 색을 보지 않아도 필수 여부가 전달되고, 일정 미반영 장소를 구분할 수 있다. 표 · 포맷 로직

U11. 공유는 목적을 먼저 고르게 하는 편이 이해하기 쉽다

현재 공유 양식은 공개 링크 생성과 공유마당 등록을 안내하고, 협업자 관리는 별도 메뉴다. 공개 안내가 없는 것은 아니다. 다만 친구에게 ‘보기만’ 보내려는 사용자와 함께 수정하려는 사용자가 어느 메뉴로 가야 하는지 스스로 구분해야 한다.

공유 진입점에서 ‘링크로 보기 / 함께 편집 / 공유마당에 공개’를 구분하고, 최종 실행 전 공개되는 일정·자료·작성자 정보와 철회 경로를 요약한다. 자료까지 모두 공개된다고 가정해서는 안 된다. 실제 권한 정책과 맞춰 안내해야 한다. 완료 기준: 사용자가 수신자의 보기/편집 가능 범위와 공유마당 노출 여부를 실행 전에 설명할 수 있다. 공유 양식

U12. 초대 입력은 개선됐지만 기존 협업자 식별은 여전히 좁다

이메일 입력을 한 줄 전체로 배치한 개선은 확인됐다. 그러나 기존 협업자 행은 넓은 권한 선택기와 제거 버튼 때문에 user2@mail... 형태로 식별 정보가 줄어든다. 비슷한 주소에서는 권한을 잘못 바꿀 가능성이 있다.

표시 이름·이메일을 위쪽에 충분히 보여주고 권한·제거를 아래에 둔다. 초대 후 사용자가 다음에 할 일, 초대 대기인지 이미 참여한 상태인지도 명확히 안내한다. 발송 여부를 이번 검사에서 확인하지 않았으므로 ‘메일이 발송된다’는 안내를 임의로 추가하지 않는다. 협업자 목록

U13. 추천을 선택한 뒤에야 ‘없음’을 알게 된다

걷기여행을 누르면 준비된 시나리오가 없다는 문구가 나온다. 명상관광은 경주 2일 코스가 표시됐다. 현재 여행은 춘천인데 첫 화면에는 지역 조건이 없다. 상단 설명은 AI가 일자별 시나리오를 만들어준다고 하지만 실제 첫 흐름은 준비된 코스 선택이다.

테마마다 이용 가능한 코스 수를 미리 표시하고, 비어 있으면 다른 테마 또는 현재 지역 장소 검색으로 연결한다. ‘준비된 추천 코스’와 ‘새로 생성’을 구분한다. 춘천 여행에는 지역 일치 코스를 우선하거나 다른 지역임을 명시한다. 완료 기준: 빈 테마를 눌러야만 공급 여부를 알 수 있는 구조를 없애고, 결과가 없을 때 유효한 다음 행동을 제공한다. 빈 결과 · 준비된 코스

U14. 자료는 존재하지만 여행 중 찾는 기준과 표시 기준이 다르다

자료 10개 화면에 사진·메모·파일 필터와 일차·장소 필터가 있다. 따라서 ‘자료 정리 기능 없음’은 아니다. 다만 현재 표시된 다수 자료는 ‘장소 없음’, 기본 파일명, 사진 격자 중심이다. 여행자는 보통 ‘오늘 숙소 체크인 자료’를 찾는다.

자료 추가 때 현재 일차·선택 장소를 제안하고, 장소 카드에서 연결 자료를 바로 연다. ‘오늘 필요한 자료’ 보기와 문서 중심 목록을 제공한다. 메모 입력에 저장·취소가 있는 것은 좋으며, 기존 메모의 즉시 편집에는 저장 상태를 더 명확히 표시한다. 예약 내용을 자동 추출하는 확장은 N04로 구분한다. 자료 · 메모 양식

U15. 공개 페이지의 주 버튼이 어두운 배경 위 어두운 글씨로 보인다

공유마당·가이드의 상단 ‘동선 만들기’가 진한 배경과 낮은 대비의 글씨로 표시됐다. 홈과 공용 헤더의 CSS 적용 범위 차이를 살펴볼 필요가 있다. landing.css에는 .landing-nav a { color: inherit; }와 .landing-btn-primary { color: #fff; }가 있고, 홈에는 추가로 .landing-page a.landing-btn-primary가 있다. 공유 페이지는 동일한 홈 래퍼가 아니므로 선택자 우선순위가 원인인 것으로 해석된다.

공용 헤더 버튼에 일관된 전경색을 적용하고 기본·hover·focus·visited 상태를 모두 확인한다. 완료 기준: 공개 페이지 어디서든 버튼 글씨가 분명하게 보인다. 수치 대비율은 이번에 측정하지 않았다. 공유마당 · 가이드 · CSS

U16. 공유 코스를 가져오기 전에 비교할 정보가 부족하다

목록은 작성자·날짜·제목·장소 요약과 ‘끌어오기’를 제공하고, 예시 배지도 보인다. 하지만 첫 카드처럼 제목에는 날짜 범위가 있고 요약은 ‘1일차 … 외 55곳’으로 나타나면 며칠 구성인지, 얼마나 빡빡한지 판단하기 어렵다. 이것만으로 원본 코스가 잘못됐다고 단정하지 않는다.

카드에 총 일수·장소 수·주요 지역·이동수단을 구조화해서 보여준다. ‘끌어오기’는 ‘내 여행으로 복사’처럼 결과를 설명하고 적용 단계에서 새 여행/현재 여행, 중복 장소 처리를 확인하게 한다. 현재 가져오기 완료 흐름은 실행하지 않았으므로 기존 확인 단계가 전혀 없다고 주장하지 않는다. 공유마당 · 필터

U17. 비용 안내는 생겼지만 가격 자체의 줄바꿈을 다듬어야 한다

Plus 화면에 ‘월 4,900원’과 매달 자동 결제·해지 가능 설명이 있어 과거 가격 미표시 문제는 개선됐다. 현재 390px에서는 ‘원’만 다음 줄로 떨어진다. 가격·주기 한 덩어리를 유지하고 보조 설명을 다음 줄로 배치한다. Free에서 가능한 범위와 업그레이드 뒤 달라지는 일을 간단히 비교하면 좋다. 이것은 이번 화면의 안내 검토이며 실제 청구 가격이나 결제 성공을 검증한 것은 아니다. 요금제

U18. 모달의 실제 모바일 접근성은 후속 검증이 필요하다

AppSheetModal.tsx는 dialog/aria-modal, 닫기 버튼, Escape 처리가 있다. 컴포넌트 안에 초기 포커스 이동·포커스 순환·닫은 뒤 포커스 복원 처리는 보이지 않는다. 접근성 트리에는 모달 뒤 앱 요소도 남았다. 이 사실만으로 터치가 배경에 통과한다고 결론 내릴 수는 없다.

실제 키보드·VoiceOver로 포커스가 모달 안에 머무는지 검증하고 공통 처리로 통일한다. 모바일 뒤로가기로 최상위 패널만 닫을지, 페이지로 이동할지도 정한다. W3C APG의 모달 패턴은 포커스 이동·내부 순환·닫기 후 복원을 설명한다. W3C 모달 패턴 · 공통 모달 코드

12. 실행 순서와 확인 기준

1단계: 일정 결과를 일관되게 만들기

U03은 마감 시점에 코드가 수정됐으므로 기존 여행·공유 화면에서 회귀 확인한다. U04의 계산 기준·시점·미리보기 상태를 통일하고 U06의 저장 표시를 붙인다. R01의 세션 복원 문제도 같은 단계에서 재현 여부를 확인한다.

2단계: 모바일 핵심 화면을 읽기 쉽게 만들기

U01·U02·U05·U07·U10을 함께 다룬다. 장소명 우선 카드, 방문 순서 기본 목록, 결과 시간표 우선, 현재 상태에 맞는 CTA 하나를 만든다. U09 조작 영역은 새 구조 안에서 검증한다.

390 × 844 외에도 360px와 320px 폭, 긴 여행명, 협업자 표시, 필수 방문, 장소 0/1/7/20개, 1일/5일/긴 다일차, 200% 텍스트 확대를 확인한다.

3단계: 공유·추천·자료의 다음 행동 정리

U11~U17과 U08을 적용한다. 빈 테마를 선택 전에 설명하고, 공유 목적을 분리하며, 자료와 일정의 연결을 강화한다. 비용 안내는 동일 화면에서 가격·주기·다음 행동이 읽히도록 한다.

4단계: 여행 중 가치 확장

N01 실행 화면 → N03 오프라인 일정팩 → N02/N05 재계획 확장 순으로 검토한다. 기능 수보다 실제 여행 현장에서 목적지 확인·자료 찾기·변경 복구가 빨라지는지를 판단한다.

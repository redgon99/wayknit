## 1. Codex의 "높음" 항목 3개 — 전부 실제 운영 환경에서 재현 확인됨

Codex는 "실제 운영 서버·DB 설정... 검증하지 않았다"고 명시했다. Supabase MCP로 직접 조회한 결과, 세 항목 전부 **추측이 아니라 지금 이 순간 살아 있는 상태**다.

| 항목 | Codex 판단 | 이번에 확인한 것 |
|---|---|---|
| 시험용 계정 로그인 | "배포 여부·계정 권한에 따라 위험 달라짐" | `list_edge_functions`로 확인 — `mock-email-login` **status: ACTIVE, verify_jwt: false**. `user1@mail.com`~`user30@mail.com` 30개 계정, 비밀번호·OTP 없이 이메일 형식만 맞으면 로그인 토큰 발급. **소스 코드 접근 없이도 30번 이내 무작위 대입으로 뚫린다** — 저장소 공개 여부와 무관한 위험 |
| 링크 추출 AI 호출 | "접근 정책 점검 필요" | `link-places-extract` **status: ACTIVE, verify_jwt: false**, 호출량 제한 없음. Anthropic 키가 설정된 지금, 누구든 익명으로 Claude 호출을 유발할 수 있음(비용 직결) |
| 카카오 REST 키 노출 | "실제 키 값은 조사 안 함" | `.env.local`에 **실제 발급된 키가 채워져 있음** 확인(`VITE_KAKAO_REST_KEY`). 배포 스크립트가 Netlify 프로덕션 환경변수를 그대로 빌드에 주입하는 구조(§9)라, 라이브 번들에도 같은 키가 그대로 들어갈 가능성이 매우 높음(번들 자체는 이번에 열어보지 않음)

**우선순위 제안:** Codex는 세 항목을 동급 "높음"으로 뒀지만, 실제 확인 결과 **`mock-email-login`이 가장 급하다** — 인증 우회 자체이고 재현 비용이 "30번 이내 무작위 대입"으로 가장 낮다. `link-places-extract`는 비용 유출, 카카오 키는 API 오남용 위험으로 그다음.

**권장 조치(간단함):** `mock-email-login`·`link-places-extract` 둘 다 `supabase/config.toml`의 `verify_jwt = false` 한 줄이 원인이다. 이 두 함수를 실제 프로덕션에서 계속 열어둘 이유가 있는지부터 확인 — 목업 로그인은 테스트 목적이라 관리자 IP·이메일 화이트리스트나 완전 비활성화를, 링크 추출은 `verify_jwt = true`(로그인 필요) 전환이나 요청당 최소한의 rate limit 추가를 검토할 것.

## 3. Codex가 다루지 않은 것 — 이 세션에서 이미 해결된 것과 아직 남은 것 구분

Codex는 정적 분석이라 "운영 DB 적용 여부는 별도 확인이 필요하다"고 여러 번 명시했다. 이 세션에서 실제로 적용·검증한 것들을 대조하면 Codex의 우려 중 상당수는 이미 해소돼 있다.

| Codex가 언급한 것 | 실제 상태(이 세션 확인) |
|---|---|
| "유료 등급 직접 변경을 막는 마이그레이션도 존재한다. 운영 DB 적용 여부는 별도 확인 필요" | §30-1에서 이미 적용·검증 완료. `profiles` 테이블의 `UPDATE` 정책 자체를 제거해 클라이언트가 `plan`을 직접 못 바꾼다(컬럼 단위가 아니라 통째로 막음 — 클라이언트가 이 테이블에 쓰기를 전혀 안 하는 걸 확인 후 결정) |
| "서버 권한 검사... 관리자 RPC 검증" | §31-2·31-8에서 감사 로그·관리자 RPC 다수 검증·보강함(A1·A3 등) |
| (언급 없음) Free 캡 우회 | §29-45에서 여행 3개·자료 20개 캡이 클라이언트 코드 3곳에서 우회 가능했던 걸 발견·수정. §30-2에서 **DB 트리거로 서버측 백스톱까지** 추가(오토세이브가 `.upsert()`라 "이미 있는 행이면 캡 검사 생략" 가드가 핵심이었음 — 안 넣었으면 기존 사용자 저장이 막히는 회귀가 났을 것) |

**남아 있다고 이 세션에서도 인정한 것(Codex와 일치):**
- Free 캡 5개 게이트 중 "일정 내보내기"·"자료 오프라인 저장"은 클라이언트 동작(파일 생성·캐시 저장)이라 자연스러운 DB 쓰기 지점이 없어 서버 백스톱을 안 만들었다(§30-2 말미) — Codex의 "저장 흐름 회귀 검증 부재" 우려와 같은 방향
- Google 검색 캡(§30-4)은 "비용 방어가 아니다"라고 스스로 문서화함 — Google Maps SDK가 API 키를 브라우저에 노출해 앱을 거치지 않고 직접 호출하면 이 서버 캡도 우회된다. **진짜 비용 방어는 GCP 콘솔의 키 제한**이고, 이건 2026-09-16에 사용자가 새 키 발급 + 리퍼러 제한으로 실제 조치 완료(§30-4 후속)

## 4. 이 세션에서 반복적으로 관찰된 패턴 3가지 — 프로세스 개선 제안

정적 분석으로는 안 보이고, 같은 세션 안에서 여러 번 겪어야 보이는 패턴들이다.

### 4.1 마이그레이션 후 PostgREST 스키마 캐시가 안 갱신될 때가 있다 (§31-12)

`CREATE OR REPLACE FUNCTION`으로 기존 RPC를 교체했는데 클라이언트가 곧바로 `404 Not Found`를 받은 사례가 있었다(`admin_moderate_report`). DB에는 함수·권한이 정상이었다 — PostgREST가 캐시를 못 읽은 것. `NOTIFY pgrst, 'reload schema'`를 두 번 보내도 안 됐고, 결국 세 번째 마이그레이션 재적용 때 같이 보낸 것이 먹혔다(원인 불명, 재현 조건도 불명).

**제안:** RPC로 노출되는 함수를 새로 만들거나 교체하는 마이그레이션에는 끝에 `notify pgrst, 'reload schema';`를 습관적으로 포함시킨다. 그래도 반영이 안 되면 Supabase 대시보드의 수동 "Reload schema cache" 버튼이 유일한 대안인데, 이건 MCP로 트리거할 방법이 없다 — 다음에 같은 문제가 나면 바로 그 경로로 안내할 것.

### 4.2 브랜드 개명(Tripasist → Wayknit) 잔재가 계속 발견된다

이번 세션에서만 두 번 나왔다: `admin_moderate_report` 함수 안에 옛 테이블명 `waymeld_trips`가 남아 `plaza_listing`(마당에서 내리기) 제재를 누를 때마다 조용히 실패하고 있었다(§31-13, 원본 마이그레이션 `20260904050000`부터 있던 버그 — 아무도 실제로 안 눌러봐서 안 들켰다). 그리고 방금 Edge Function 목록 조회에서 여러 함수의 `entrypoint_path`가 `file:///project/tripasist2/...`로 남아 있는 걸 봤다(배포 캐시 경로라 동작에는 영향 없지만, 개명이 완전하지 않다는 신호).

**제안:** `waymeld_trips`·`tripasist`·`WayMeld` 같은 옛 이름을 `supabase/migrations/`·`supabase/functions/` 전체에서 한 번 훑는 일회성 감사를 권한다(`grep -rln`으로 몇 분이면 끝남). 지금까지는 "실제로 그 기능을 눌러본 사람이 있어야만" 발견됐다 — 조용히 실패하는 코드 경로가 더 있을 가능성이 있다.

### 4.3 "다음에 지운다"고 커밋 메시지에 적은 임시 코드가 안 지워진 채 배포된다

§2의 AI 일정 생성 `isAdmin` 게이트가 정확히 이 경우다. `HANDOFF.md`가 "다음 세션 시작점"을 꾸준히 갱신해온 덕에 이번 세션 내의 작업들은 대부분 추적됐지만, **커밋 메시지 안에만 적힌 "이 조건은 나중에 지운다" 같은 자기 자신에게 남긴 메모는 HANDOFF에 옮겨 적지 않으면 다음 세션(사람이든 AI든)이 놓친다.**

**제안:** `// TODO(제거 조건): ...` 같은 코드 주석을 심을 때, 그 조건이 실제로 충족된 다음 커밋에서 확인하는 절차를 만들거나, 최소한 HANDOFF의 "남은 것" 목록에 "Step N 완료 후 X 위치의 임시 게이트 제거" 형태로 명시적으로 옮겨 적는 관례를 권한다. 지금은 grep으로 우연히 찾아야 한다.

## 5. Codex 리포트에 동의하는 것 — 재반복하지 않고 우선순위만 재확인

- **린트 미실행·자동 회귀 테스트 부재**: 이 세션 내내 `tsc --noEmit`·`npm run build`만으로 검증했고(사용자 지시로 자체 브라우저·API 검증도 안 함), 이건 "빠르지만 얕다." Codex의 "핵심 흐름부터 회귀 테스트"라는 방향에 동의한다. 다만 이 프로젝트 특유의 위험 지점(여행 저장 오프라인 폴백, 공동편집 실시간 병합, Free 캡 3종)부터 우선순위를 매길 것을 제안한다 — 이 셋이 이번 세션에서 실제로 버그가 났던 영역이다(§29-31 오프라인, §29-45 캡 우회).
- **대형 파일 책임 집중**(`PlannerPage.tsx` 3,828줄 등): 동의. 이번 세션에서도 이 파일을 여러 번 열 때마다 원하는 로직을 찾는 데 시간이 들었다.
